## 1. 先判断：项目在不在跑

```powershell
$ports = 8001,5173,8002,5174,8003,5175,8080
Get-NetTCPConnection -State Listen -ErrorAction SilentlyContinue |
  Where-Object { $_.LocalPort -in $ports } |
  Select-Object LocalPort, LocalAddress, OwningProcess,
    @{n='Process';e={(Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue).ProcessName}} |
  Sort-Object LocalPort | Format-Table -AutoSize
```

输出为空 = 一个都没跑。

## 2. 查看端口占用

### 2.1 `netstat`：最通用，兜底首选

```cmd
netstat -ano | findstr :8001
```

末列是 PID：

```
  TCP    127.0.0.1:8001    0.0.0.0:0    LISTENING    30800
```

`Get-NetTCPConnection` 查不到时（个别非托管/系统级进程），一定回来试 `netstat`。

### 2.2 `Get-NetTCPConnection`：带进程名更直观

```powershell
Get-NetTCPConnection -LocalPort 8001 -State Listen |
  Select-Object LocalAddress, LocalPort, OwningProcess,
    @{n='Process';e={(Get-Process -Id $_.OwningProcess).ProcessName}},
    @{n='Path';e={(Get-Process -Id $_.OwningProcess).Path}}
```

### 2.3 拿到 PID 后反查身份

**命令行才是判断归属的唯一依据**：

```powershell
Get-CimInstance Win32_Process -Filter "ProcessId=30800" |
  Select-Object ProcessId, ParentProcessId, Name, CreationDate, CommandLine | Format-List
```

### 2.4 按项目路径反查：最可靠

```powershell
Get-CimInstance Win32_Process |
  Where-Object { $_.CommandLine -match 'Medical-RAG' } |
  Select-Object ProcessId, ParentProcessId, Name, CommandLine | Format-List
```

结果里会混入无关进程，务必排除：

| 混入项 | 识别特征 |
| --- | --- |
| VS Code | `Code.exe "F:\Medical-RAG"`，编辑器不是应用 |
| Agent/Codex 运行时 | 命令行含 `cua_node`、`.tmp*`、`node_repl` |
| DSH / 终端自身 | 你执行的这条命令本身就含 `Medical-RAG` 字面量 |

**判据**：命令行里跑的是不是项目自己的服务（`uvicorn` / `vite` / `esbuild`）。

### 2.5 看清进程树

`uvicorn --reload` 与 `vite` 都是**多层进程**，只看持有端口的 PID 必漏。

```powershell
$target = 30800
$p = Get-CimInstance Win32_Process -Filter "ProcessId=$target"
"PID=$($p.ProcessId) PPID=$($p.ParentProcessId) $($p.Name)"
$par = Get-CimInstance Win32_Process -Filter "ProcessId=$($p.ParentProcessId)" -ErrorAction SilentlyContinue
if ($par) { "PARENT: PID=$($par.ProcessId) $($par.Name)" } else { "PARENT: (已退出)" }
```

实测的两种结构：

```
uvicorn --reload
  父 reloader  ← 命令行含项目路径，负责监听文件变化
  └─ 子 server  ← **持有端口的是这一层**，命令行可能不含项目路径
     └─ 孙 multiprocessing spawn worker（父变了就重建）

vite
  node vite.js ← 持有端口
  └─ esbuild.exe --service=... --ping
```

**要点**：优先定位**父 reloader**，因为它的命令行稳定含项目路径，最好认。

### 2.6 WSL 里的端口：`wslrelay` 是转发，不是真凶

Windows 上看到端口被 `wslrelay.exe` / `wslservice.exe` 占用，说明真正的监听者在 **WSL 内部**。

```powershell
wsl.exe -e bash -lc "ss -ltnp | grep -E ':(5173|5174|8001)'"
```

```
LISTEN 0 512 0.0.0.0:5173 0.0.0.0:* users:(("node",pid=88769,fd=11))
```

再确认它跑的是哪个项目：

```powershell
wsl.exe -e bash -lc "ps -ef | grep -E 'vite|node' | grep -v grep"
```

**注意 WSL 输出的编码坑**：`wsl.exe` 自身输出是 UTF-16，与子进程的 UTF-8 混在一起，直接经 PowerShell 管道处理会乱码。**让 WSL 内部先写文件，再读回**：

```powershell
wsl.exe -e bash -lc "ss -ltnp | grep :5173 > /tmp/o.txt 2>&1" 2>$null
wsl.exe -e bash -lc 'cat /tmp/o.txt' 2>$null
```

### 2.7 Docker

`medical-platform-deploy` 用 `docker compose` 起 Nginx（8080）。容器占端口时用 Docker 自己的命令，**不要 `taskkill`**：

```powershell
docker ps
docker compose -f F:\Medical-RAG\medical-platform-deploy\compose.yaml down
```

报 `failed to connect to the docker API` = 守护进程没启动，此时容器不可能占端口。

## 3. 怎么关闭占用端口的程序（核心）

「关闭端口」的本质是**关闭占用该端口的进程**。端口本身没有独立开关，进程退出后监听自动释放。

### 3.1 三步法

```powershell
# 第 1 步：找出占用端口的 PID
netstat -ano | findstr :8001

# 第 2 步：确认这个 PID 到底是什么（关键！别跳）
Get-CimInstance Win32_Process -Filter "ProcessId=30800" |
  Select-Object ProcessId, ParentProcessId, Name, CommandLine | Format-List

# 第 3 步：终止整棵进程树
taskkill /PID 30800 /T /F
```

**为什么必须做第 2 步**：端口和项目不是一一对应的，看错 PID 会误杀别人正在用的服务（见 4.2、4.3）。

### 3.2 `taskkill /T /F`：推荐做法

```powershell
taskkill /PID <PID> /T /F
```

- `/T` 终止整棵进程树（父 + 子 + 孙）
- `/F` 强制终止

**优先杀树的「根」**，即命令行含项目路径的那个父进程。实测证明 `/T` 比手工列举 PID 更可靠——它会连同**扫描之后新生成**的子进程一起收掉。

本题实测输出：

```
taskkill /PID 16580 /T /F
  SUCCESS: PID 28892 (child of 30800) terminated   ← 扫描时还不存在
  SUCCESS: PID 30800 (child of 16580) terminated
  SUCCESS: PID 16580 (child of 18668) terminated
```

### 3.3 `Stop-Process`：简单但**不杀子进程**

```powershell
Stop-Process -Id 30800 -Force
```

只适合无子进程的单体目标。用于 uvicorn/vite 会留下孤儿 worker 继续占端口。

### 3.4 按端口一键关闭

已确认归属后：

```powershell
$port = 8001
Get-NetTCPConnection -LocalPort $port -State Listen -ErrorAction SilentlyContinue |
  ForEach-Object { taskkill /PID $_.OwningProcess /T /F }
```

### 3.5 关闭 WSL 里的进程

**必须在 WSL 内部 kill，不要在 Windows 杀 `wslrelay.exe`**（杀它会影响整个 WSL 实例的端口转发，而 WSL 里的进程还活着）。

```powershell
# 查 PID
wsl.exe -e bash -lc "ss -ltnp | grep :5173 > /tmp/o.txt 2>&1"; wsl.exe -e bash -lc 'cat /tmp/o.txt' 2>$null

# 按进程组关闭（推荐，连带子进程）
wsl.exe -e bash -lc "kill -TERM -- -<PGID>"

# 或按 PID 关闭
wsl.exe -e bash -lc "kill -TERM 88769"
```

实战建议：先看进程组，再整组终止。

```bash
PGID=$(ps -o pgid= -p 88769 | tr -d ' ')   # 得到 vite 所属进程组
kill -TERM -- -"$PGID"                      # 整组 TERM，避免漏掉 esbuild
```

若目标的父进程是 `/init`（`ps -o cmd= -p <PPID>` 显示 `/init`），说明它是某个 WSL 终端会话的主进程，杀掉它就是关掉那个终端的服务，**不要连带杀 `/init`**。

### 3.6 关闭后必须复查

```powershell
# 端口是否释放（无输出 = 已释放）
Get-NetTCPConnection -LocalPort 8001 -State Listen -ErrorAction SilentlyContinue

# 进程是否还在（无输出 = 已终止）
Get-Process -Id 30800 -ErrorAction SilentlyContinue
```

命令没报错 ≠ 关掉了。**必须回查端口和进程**。

### 3.7 需要管理员权限吗

- 自己启动的 node / python：**不需要**
- 系统服务、其他用户账户的进程：需要**管理员身份**终端，否则 `Access is denied`
- WSL 内进程以你的 WSL 用户身份运行：通常不需要

## 4. 六个必须避开的坑

### 4.1 绝不 `taskkill /IM node.exe /F`

一条命令杀掉**所有** Node 进程，包括 VS Code 语言服务、其他项目 dev server、各类 Agent 运行时。**永远按 PID 精确关闭。**

### 4.2 端口 ≠ 项目归属，必须看命令行

**实测案例**：`5174` 上的 vite，命令行指向

```
F:\Medical-RAG\medical-knowledge-web\node_modules\vite\bin\vite.js --port 5174
```

即 `medical-knowledge-web` 跑在了 `5174`，而按端口表 `5174` 属于 `medical-agent-web`。**只按端口表判断就会认错项目。**

佐证：该 vite 启动后打印 `Local: http://127.0.0.1:5174/knowledge/`，base 为 `/knowledge/`，与 knowledge-web 吻合。

**结论**：端口表只用于「快速发现」，最终归属以命令行（及启动日志的 base 路径）为准。

### 4.3 相对路径启动会让命令行「失联」

若用相对路径启动，命令行里**不含项目路径**：

```
node.exe .\node_modules\vite\bin\vite.js --host 127.0.0.1 --port 5174
```

此时无法从自身命令行证明归属。**补救判据**：看它的**子进程**——vite 拉起的 `esbuild.exe` 命令行是绝对路径，含完整项目路径，可反向证明 vite 的归属。

```powershell
# 子进程命令行含项目路径 -> 可证明父进程归属
Get-CimInstance Win32_Process -Filter "ProcessId=<vite PID>" | % { $_.ProcessId }
Get-CimInstance Win32_Process | ? { $_.ParentProcessId -eq <vite PID> } |
  Select-Object ProcessId, Name, CommandLine
```

`npm run dev` 启动时 `.bin` 垫片通常给出绝对路径，一般不会踩这个坑；手工 `node .\...` 启动会踩。

### 4.4 同一端口上可能有别的项目

**实测案例**：本机 `5173` 曾被另一个项目占用：

```
"node" "F:\BrainBloodAgent\RAG0917\code\medical-qa-agent\frontend\node_modules\...\vite\bin\vite.js" --host 127.0.0.1 --port 5173 --strictPort
```

这**不是** Medical-RAG。它的父进程是 `cmd.exe /c vite --host 127.0.0.1 --port 5173 --strictPort`。

**结论**：端口相同不代表项目相同。关之前一定确认命令行路径。（本例中该进程按计划保留未动。）

### 4.5 别杀代理、编辑器、Agent 运行时

| 类别 | 典型进程 | 后果 |
| --- | --- | --- |
| 代理 | `verge-mihomo`(7897)、`clash-verge`(4994) | 立即断网 |
| 编辑器 | `Code.exe`、`cursor.exe` | 编辑器异常 |
| Agent 运行时 | 命令行含 `cua_node`、`node_repl`、`--eval` | 工具链中断 |
| WSL 转发 | `wslrelay.exe`、`wslservice.exe` | WSL 端口转发失效 |

### 4.6 进程树会「再生」

`uvicorn --reload` 的 worker 在文件变化时会重新 spawn。只杀 worker 不杀 reloader，它立刻重建一个新 worker 继续占端口。**必须从根杀起。**

### 附：写脚本时的一个 PowerShell 5.1 陷阱

`[ordered]@{}` 用**整数键**时，索引器会被解析成「按位置取第 N 项」而非「按键取值」，导致取值恒为空：

```powershell
$m = [ordered]@{ 8001 = 'A' }
$m[8001]        # => '' （空！不是 'A'）
$m.Values       # => A   （值其实在）
$m.Contains(8001)  # => True
```

**规避**：整数键就用普通 `@{}`，或者干脆用对象数组。本项目脚本已改用对象数组。

## 5. 实战案例

### 5.1 第一轮：关闭 Windows 侧本项目服务

| 端口 | PID | 进程 | 归属判定 |
| ---: | ---: | --- | --- |
| 8001 | 31420 | `python.exe` (uvicorn) | ✅ `medical-knowledge-api` |
| 5174 | 18160 | `node.exe` (vite) | ✅ `medical-knowledge-web` |
| 5173 | 33584 | `wslrelay.exe` | ❌ WSL 内其他项目，未动 |
| 8002/8003/5175/8080 | — | — | 未运行 |

进程树：

```
medical-knowledge-api（8001）
PID 29624  F:\Medical-RAG\medical-knowledge-api\.venv\Scripts\python.exe -m uvicorn ... --port 8001 --reload
└─ PID 31420  uv\python\...\python.exe -m uvicorn ... --port 8001 --reload   ← 持有 8001
   └─ PID 19664  multiprocessing spawn worker

medical-knowledge-web（5174）
PID 18160  node.exe ...\medical-knowledge-web\node_modules\vite\bin\vite.js --port 5174
└─ PID 21904  esbuild.exe --service=0.25.12 --ping
```

执行 `taskkill /PID 29624 /T /F` 与 `taskkill /PID 18160 /T /F`，实际终止 **6 个**进程，比首扫多两个（31564、29028）——**这就是用 `/T` 而非逐个 PID 的价值**。

### 5.2 第二轮：关闭 WSL 内的项目

发现 `/home/jzdf/code/JLAIharnessos/web` 的 vite 占用 5173（经 `wslrelay` 映射到 Windows）。

```
88762  /init                      ← WSL 终端会话初始化进程，不能动
└─ 88763  bun run dev --host 0.0.0.0    ← PGID 88763
   └─ 88769  node .../JLAIharnessos/web/node_modules/.bin/vite  ← 持有 5173
      └─ 88794  esbuild --service=0.21.5 --ping
```

确认 `vite(88769)` 的 PGID 正是 `88763`（= `bun`），于是整组终止：

```bash
kill -TERM -- -88763
```

结果：WSL 内 5173 释放、`JLAIharnessos` 无残留进程，Windows 侧 5173 同步释放。

### 5.3 第三轮：脚本实测

用真实服务实测 `stop-medical-rag.ps1`，识别结果：

- `[确认]` uvicorn 父进程 16580 → 树杀，连带 server(30800)、worker(28892)
- `[确认]` vite 15036 → **自身命令行不含项目路径**（相对路径启动），靠子进程 `esbuild.exe` 命令行含项目路径**证明归属**后关闭
- 去重生效：跳过 esbuild(23300)，交给 vite 的进程树一并终止
- `[未确认]` 5173 的 `medical-qa-agent` → 正确判定为其他项目，未动

### 5.4 最终状态

| 端口 | 状态 |
| ---: | --- |
| 8001 / 8002 / 8003 | 空闲 |
| 5174 / 5175 | 空闲 |
| 8080 | 空闲 |
| 5173 | 被**其他项目**（`medical-qa-agent`）占用，按设计未动 |

## 6. 一键脚本

同目录 `stop-medical-rag.ps1`，多重归属确认 + 白名单保护，已用真实服务实测。

```powershell
# 预览会关掉哪些（推荐先跑这个）
powershell -NoProfile -ExecutionPolicy Bypass -File F:\Medical-RAG\docs\stop-medical-rag.ps1 -DryRun

# 确认后执行
powershell -NoProfile -ExecutionPolicy Bypass -File F:\Medical-RAG\docs\stop-medical-rag.ps1

# 连 Docker 部署栈一起停
powershell -NoProfile -ExecutionPolicy Bypass -File F:\Medical-RAG\docs\stop-medical-rag.ps1 -IncludeDocker
```

归属判定分三档：

| 档位 | 判据 | 默认行为 |
| --- | --- | --- |
| `[确认]` | 自身命令行含项目路径 | 关闭 |
| `[确认]` | 自身无路径，但子进程命令行含项目路径 | 关闭 |
| `[未确认]` | 占用项目端口但无法证明归属 | 仅告警，需 `-Force` |
| `[保护]` | 命中白名单（编辑器/代理/WSL 转发） | 永不关闭 |
