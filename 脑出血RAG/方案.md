# 脑出血 RAG 项目总方案

> 本文是项目的顶层架构基准。详细数据模型、接口和事件协议以子文档《医学专病知识库 ／ Agent ／ 测评平台开发规格说明》为准。

## 一、项目形态

项目采用 **6 个独立业务仓库 + 1 个集成部署仓库**：

|仓库|技术栈|开发端口|
| ------| --------------------------------------------| ---------: |
|​`medical-knowledge-api`|FastAPI + PostgreSQL + Qdrant + MCP Server|8001|
|​`medical-knowledge-web`|Vue 3 + TypeScript + Element Plus|5173|
|​`medical-agent-api`|FastAPI + PostgreSQL + LLM + 多 MCP Client|8002|
|​`medical-agent-web`|Vue 3 + TypeScript + Element Plus|5174|
|​`medical-evaluation-api`|FastAPI + PostgreSQL + Celery + Redis|8003|
|​`medical-evaluation-web`|Vue 3 + TypeScript + Element Plus|5175|
|​`medical-platform-deploy`|Docker Compose + Nginx|8080|

Knowledge API 与 Knowledge Web 必须是两个独立仓库；其他前后端同样独立开发、测试和发布。各服务禁止共享 ORM 模型或跨库直连。

## 二、职责边界

### 医学知识服务

- 负责文献管理、PDF 上传、PDF 转 Markdown、章节恢复、分块、PICO/Outcome 结构化、人工审核、混合检索和 MCP Server。
- 常规 PDF 使用 MinerU；复杂版式和表格使用 Docling；扫描件按需增加 OCR。
- 第一版 MVP 包含 PDF 上传、DOI 元数据获取和文件夹/集合管理。
- 不存储 Agent 会话或测评任务。

### 医学 Agent 服务

- 负责 LLM 调用、Prompt/Skill、会话与消息持久化、多 MCP Client、工具调用执行、引用记录和 SSE 输出。
- 可以同时连接 Knowledge MCP、`medical-mcp`、PubMed MCP 等多个 MCP Server。
- 禁止直接连接 `knowledge_db`，也禁止维护第二套文献索引或在 Agent 内部运行独立向量检索。
- 引用必须保留稳定标识：`document_id`​、`document_version_id`​、`chunk_id`​、`evidence_span_id`​、`index_version`。
- MCP 检索失败时允许模型基于自身知识回答，但必须明确标注“未经文献验证”，且不得伪造引用。

### 医学测评平台

- 负责题库、标准答案、批量运行、指标、结果分析。
- 负责 Agent 中跨步骤的控制循环以及安全/治理策略；Agent API 提供原子化的模型、会话、MCP 调用和记录能力。
- 通过公开 API 调用 Knowledge API 和 Agent API，不直接访问其他服务数据库。

## 三、服务通信

|调用方|被调用方|协议|用途|
| ----------------| -----------------| -----------------| --------------------------------------------|
|Knowledge Web|Knowledge API|REST|文献、解析、结构化、检索|
|Agent Web|Agent API|REST + SSE|会话、问答、引用和运行轨迹|
|Evaluation Web|Evaluation API|REST + 轮询/SSE|题库、任务和结果|
|Agent API|多个 MCP Server|MCP|Knowledge 证据、PubMed、药物和其他外部证据|
|Evaluation API|Knowledge API|REST|检索测评和证据核验|
|Evaluation API|Agent API|REST + SSE|控制循环、批量问答和治理|

跨服务数据格式通过 OpenAPI、Pydantic Schema 和版本化协议约束。

## 四、统一入口

- ​`/knowledge/` → Knowledge Web
- ​`/agent/` → Agent Web
- ​`/evaluation/` → Evaluation Web
- ​`/api/knowledge/` → Knowledge API
- ​`/api/agent/` → Agent API
- ​`/api/evaluation/` → Evaluation API

三个 Vue 项目分别配置 Vite `base` 和 Vue Router 基路径，由 Nginx 统一代理。

## 五、统一工程约束

- 后端统一使用 Python 3.12、FastAPI、Pydantic v2、SQLAlchemy 2、PostgreSQL 16 和 Alembic。
- 数据库结构变更只能通过 Alembic migration。
- 配置全部来自环境变量；仓库提供 `.env.example`，不得提交密钥。
- 每个后端拥有独立数据库、Dockerfile、compose.yaml、Alembic、pytest 和 README。
- API 统一使用 `/api/v1`。
- 医学结论围绕可追溯证据设计，所有关键模型、Prompt、Schema 和索引均需版本化。

## 六、开发顺序

1. Knowledge API：文献、PDF、DOI、文件夹、解析、分块和数据库。
2. Knowledge Web：上传、管理、解析状态和 Chunk 查看。
3. 医学结构化与审核。
4. 混合检索和 Knowledge MCP。
5. Agent API / Web：多 MCP、会话、运行记录、引用和 SSE。
6. Evaluation API / Web：控制循环、安全治理、批量测评和指标。
7. 集成部署、日志、备份和端到端测试。
