# 会话管理

‍

## 一、统一命名

会话资源统一命名为 `conversation`​，数据库表为 `conversations`​，请求字段为 `conversation_id`​。旧版 `session`​、`sessions`​、`session_id` 仅作为历史术语，不再进入新代码和接口。

## 二、数据模型

### `conversations`

- ​`id: UUID`
- ​`title`
- ​`user_id`
- ​`created_at`
- ​`updated_at`

### `messages`

- ​`id: UUID`
- ​`conversation_id: UUID`
- ​`role: user | assistant | system | tool`
- ​`content`
- ​`created_at`

### 运行与引用

每次问答另外创建 `agent_runs`​；MCP 调用写入 `tool_calls`​；回答引用写入 `answer_citations`​。不要把运行轨迹和引用全部塞进 `messages` 的 JSON 字段。

## 三、API

- ​`POST /api/v1/conversations`：显式创建会话。
- ​`GET /api/v1/conversations`：分页列出会话。
- ​`GET /api/v1/conversations/{id}`：获取会话与消息。
- ​`POST /api/v1/chat`​：使用已有 `conversation_id` 发起问答。
- ​`POST /api/v1/chat/stream`：流式问答。

首次问答前应先创建 conversation。无效或无权访问的 `conversation_id` 返回 404/403，不静默创建新会话。

## 四、上下文窗口

- 按 `created_at` 倒序取最近 N 轮，再恢复为正序。
- N 由环境变量 `MAX_HISTORY_TURNS` 配置。
- 长病历优先按 token 预算裁剪，不只按固定轮数。
- 数据库保存完整历史；上下文裁剪不删除原始消息。

## 五、模型与会话

模型由环境变量配置。每个 `agent_run` 记录实际使用的 provider、model、Prompt 版本和 Skill 版本；允许部署配置变化后继续旧 conversation，但必须通过 run 记录保证可追溯。

## 六、用户隔离与安全

- ​`conversations.user_id` 必填。
- 所有读取、写入、删除都校验当前用户。
- UUID 不能替代鉴权。
- Evaluation API 使用服务身份调用，并记录 actor。

## 七、过期与清理

TTL 来自 `CONVERSATION_TTL_HOURS`​。清理任务可以归档或删除过期 conversation 和 message，但不得删除仍处于保留期内的 `agent_runs`​、`tool_calls` 和审计数据。

## 八、SSE 关联

流式事件使用 `conversation_id`​ 和 `run_id`​ 关联。事件名称固定为 `run_started`​、`tool_started`​、`tool_completed`​、`answer_delta`​、`citations`​、`run_completed`​、`run_failed`。

## 九、数据库要求

会话数据存入独立 PostgreSQL `agent_db`​，所有表结构变更使用 Alembic。禁止用 SQLite 或 `Base.metadata.create_all()` 作为正式建表方式。
